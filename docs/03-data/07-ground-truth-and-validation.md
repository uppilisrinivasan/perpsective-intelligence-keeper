# Ground truth and validation

## 1. Separation

`data/ground_truth/` is written only by datagen (G10) and read only by `keeper.eval` and tests. An import-linter contract forbids any module except `keeper.eval` and `keeper.datagen` from importing `keeper.eval.truth` or opening paths under `ground_truth/`. The loader (FR-DATA-6) skips the folder.

## 2. Files

| File | Content (JSON Lines unless stated) |
|---|---|
| `slots.json` | The resolved slot definitions (from the scenario plus world wording) |
| `pr_slots.jsonl` | `{pr_number, slot, variant, present: true, locations: [{path, line}], flagged_by: [login], addressed: bool, outcome: null|{kind, issue_number|pr_number}}` |
| `comment_truth.jsonl` | `{comment_kind: review_comment|review|issue_comment, id, pr_number, author, planted: [{slot, severity}], social: bool, question: bool}`: what each human comment was generated to express |
| `pr_lanes.jsonl` | `{pr_number, split: train|holdout|live, expected_lane, expected_signals: [...], expected_handoff: login|null}`. For history PRs, the expected lane is computed by code from the slots (edge slots flagged by the maintainer → edge, and so on) under the same rules as routing, as if they were open. |
| `outcomes.jsonl` | `{pr_number, outcome, cause_slot|null, base_rate: bool}` |
| `learner.jsonl` | `{session, item_pr, planted_catches: [slot], own_eye: [slot]}` |
| `eval_thresholds.json` | A copy of `config/eval.yaml` at generation time |

## 3. Evaluation harness (`./run.sh --eval`, `python -m keeper.eval`)

It runs Keeper's pipeline from the snapshot (no model calls) or live (`--live`), and compares the results with the ground truth:

| Metric | Compares | Threshold (`config/eval.yaml`) |
|---|---|---|
| Extraction precision and recall | Extracted human findings against `comment_truth.planted` (per comment, by slot category) | ≥ 0.90 / ≥ 0.85 |
| Judge agreement | `match_findings` decisions against slot equality on H-vs-C pairs | κ ≥ 0.70 |
| Lens item coverage | Each maintainer edge slot (E1–E8) corresponds to ≥ 1 validated item (by exemplar membership ≥ 60%) | ≥ 7 of 8 |
| Blind-spot items | B1 and B2 present as blind-spot items | 2 of 2 |
| Bias detection | X1 is `bias_suspected`; no other item is | exact |
| Drift | D1 is in v1's G for the held-out period; D1 is an item in v2 | both |
| Routing accuracy (live queue) | PR lanes against `pr_lanes` for the `live` split | macro-F1 ≥ 0.8; unknown recall = 1.0 |
| Routing accuracy (held-out) | as above, for `holdout` | macro-F1 ≥ 0.7 |
| Edge map | Planted high-value areas in the top 4 | ≥ 3 |
| Fidelity pass | The Proof run on the held-out set passes | pass |
| Fix success | The share of fixable live-queue findings with a passing fix | ≥ 0.7 |

The report is written to `data/generated/eval_report.json` (committed for the snapshot) and printed as a table. A threshold failure exits non-zero.

## 4. Linking baseline findings to slots (for judge validation)

Baseline findings are not planted, so to compute judge agreement, code labels each baseline finding with a slot if its anchor is within ±3 lines of a slot location and its category is compatible, or if the slot's deterministic check (V5) flags the same lines. Otherwise it is labelled `none`. A pair of (human finding, baseline finding) is "truly the same concern" when both have the same slot. Agreement is computed over all candidate pairs the matcher generated.

## 5. Why this is a fair test of Keeper

- The lens never sees the slots. It sees only comments, diffs and outcomes, exactly as for a real repository.
- Rates are noisy (sampled), outcomes include base-rate noise, the maintainer misses some of their own edge concerns (`flag_rate` < 1), and replies and social comments dilute the signal.
- The baseline is the real model; edge slots it catches are reported as such.
- Held-out PRs are generated by the same process but are never used for building or tuning. Prompt changes are developed on the `train_v1` split only, and `--eval` prints a warning if prompt versions changed after the last held-out evaluation.

## 6. Known limitations of the synthetic evaluation (published in Proof → "How we measure")

1. The world is designed to have a residual, so a positive result on the demo shows the **mechanism works when a residual exists**. It does not prove that real maintainers have one. The real-repository run addresses that.
2. Review voices are model-written, and may be more uniform than real ones.
3. Outcome rates are scenario parameters, not measurements.
