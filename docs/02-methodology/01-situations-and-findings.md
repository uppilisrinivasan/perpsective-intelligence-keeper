# Situations and findings

## 1. The situation: a pull request

A situation is one PR at one **head SHA**. If a contributor pushes again, analysis is re-run for the new head, and old analyses are kept with their SHA.

The **PR context block** is the exact, size-bounded text given to both the baseline and the lens review. It is built by `keeper.analysis.context.build_context(pr, head_sha)`:

| Part | Content | Bound (config `context.*`) |
|---|---|---|
| Header | Repository name, PR number, title, labels, base branch, author association, draft flag | — |
| Description | PR body, with HTML comments and the PR template's unchanged boilerplate stripped | `max_description_chars` (4,000) |
| Files | List of `{path, status, additions, deletions, binary}` | all |
| Diff | Unified diff per file, with hunk headers and line numbers on the new side, as `L123 +code`. Binary files are listed but not shown. | `max_diff_lines` (1,500). Above it, the largest generated or lock files are dropped first, then files are truncated with "[… N lines omitted]". |
| CI | Check-run names and conclusions at the head SHA | — |
| Repository notes | `CONTRIBUTING.md` sections on review policy, if present | `max_repo_notes_chars` (2,000) |

Not included: the author's login and history, or any reviews or comments on the PR. The reviewer must form its own view, as the human did, from the change. *Rationale:* including existing human comments would leak H into C and L.

## 2. The finding

A finding is one noticed thing. All four sources (human, baseline, lens, learner) produce the same structure, so they can be matched.

```jsonc
{
  "id": "fnd_01J…",                         // ULID, generated by code
  "situation": {"project_id": "prj_…", "pr_number": 212, "head_sha": "9f3c…"},
  "source": "human",                        // human | baseline | lens | learner
  "person_id": "per_…",                     // for human and learner; null otherwise
  "anchor": {
    "scope": "line",                        // line | file | pr
    "path": "strata/include.py",            // null when scope = pr
    "side": "RIGHT",                        // RIGHT (new) | LEFT (old)
    "start_line": 41, "end_line": 47        // new-file line numbers for RIGHT
  },
  "category": "security",                   // from config/taxonomy.yaml
  "severity": "major",                      // blocker | major | minor | nit
  "kind": "change_request",                 // see §4
  "statement": "Resolved include path can escape the project root via '..' segments.",
  "rationale": "…",                         // optional; why it matters
  "suggestion": "Resolve with Path.resolve() and check is_relative_to(root).",  // optional
  "substantive": true,                      // derived from category, see §3
  "confidence": "high",                     // lens and baseline only
  "refs": {
    "comment_ids": [884123], "review_ids": [], "issue_comment_ids": [],     // human
    "lens_item_ids": [], "exemplar_finding_ids": [],                         // lens
    "tool": null                                                             // baseline static tool name, e.g. "bandit:B108"
  },
  "llm_call_id": "llm_…",                   // provenance; null for tool findings
  "created_at": "2025-03-04T10:22:31Z"      // when the human wrote it, or when it was generated
}
```

### 2.1 Anchors

- **Human:** from the review comment's `path`, `line`, `start_line` and `side`. If `line` is null (an outdated comment), use `original_line` mapped through the PR's commits where possible; otherwise `scope = file`. A `subject_type: "file"` comment gives `scope = file`. Review bodies and conversation comments give `scope = pr`, unless the extractor finds an explicit path and line mention (for example "include.py:41") and validates it against the diff.
- **Baseline and lens:** the model returns `path`, `start_line` and `end_line`. Code validates them against the diff. A line outside any hunk is snapped to the nearest hunk in the same file if within `anchor_snap_lines` (5); otherwise it is downgraded to `scope = file`.
- **Learner:** clicked lines in the UI, or PR-level.

### 2.2 Merging within one source

Duplicate findings from one source on one PR (the same anchor ± 3 lines, the same category, and statement similarity ≥ 0.8 by TF-IDF cosine) are merged by code, keeping the earliest and unioning the refs.

## 3. The concern taxonomy (`config/taxonomy.yaml`)

The categories combine what reviewers actually comment on (Bacchelli & Bird: defects are only a minority of review comments) with what the papers say generic AI misses (project invariants, history, threat model).

| Category | Substantive | Description for the extractor and reviewers | Example |
|---|---|---|---|
| `correctness` | yes | Logic errors, wrong results, edge cases, error handling | "Off-by-one on the last line when there's no trailing newline" |
| `api_compat` | yes | Public API changes, backward compatibility, deprecation policy | "Removing `load(strict=)` breaks callers; deprecate first" |
| `invariant` | yes | Project-specific rules the code must keep (round-trip, no runtime deps, supported versions) | "Dump must preserve comment order; this re-sorts keys" |
| `security` | yes | Threat-model issues: untrusted input, path traversal, injection, secrets, DoS | "`..` in includes escapes root" |
| `performance` | yes | Hot paths, complexity, allocations, I/O | "This regex runs per character in the tokenizer" |
| `history_context` | yes | References to past decisions, incidents or reverted attempts | "We removed this cache in #212 because it raced" |
| `tests` | yes | Missing, weak or wrong tests | "Add a test for an empty include" |
| `design` | yes | Structure, naming of concepts, responsibilities, simplicity | "This belongs in the resolver, not the parser" |
| `docs` | yes | User-facing docs, changelog, docstrings of the public API | "Add a changelog entry under Unreleased" |
| `build_release` | yes | Build scripts, packaging, CI workflows, release tooling | "Why does the release script now fetch a tarball?" |
| `dependency` | yes | New or changed dependencies, pins, licences | "We don't take runtime deps" |
| `question` | yes, if it challenges a choice; no if clarifying only (the extractor decides) | Questions to the author | "Why not reuse `Resolver.normalize`?" |
| `style` | no | Formatting, naming nits, lint-level issues | "Nit: trailing whitespace" |
| `social` | no | Thanks, approval, process chatter | "Thanks! LGTM" |

The taxonomy file also defines, per category: a display label, a short UI description, a colour token, and `fixable_default` (whether Keeper may try a fix). `build_release` and `dependency` have `fixable_default: false`: changes to build, release and dependency declarations are exactly where a human must decide, so Keeper proposes only text for those. `security` is fixable, because a security fix is verified by a regression test like any other, but its fixes are always shown for review and never counted as "Handled for you".

## 4. Kinds

| Kind | Source | Meaning |
|---|---|---|
| `comment` | human, baseline, lens | A remark that does not block |
| `change_request` | human (from a review with `state = CHANGES_REQUESTED`, or wording like "please change"), baseline and lens (severity ≥ major) | Asks for a change before merge |
| `rejection` | human | A reason given for closing the PR unmerged |
| `question` | human, lens | A challenge question |
| `maintainer_fix` | human | Derived from a commit the maintainer pushed to the PR |
| `tool` | baseline | A static-tool hit |

## 5. Severity

| Severity | Meaning | Human mapping heuristics (applied by the extractor, then checked by code) |
|---|---|---|
| `blocker` | Must not merge | In a `CHANGES_REQUESTED` review and the category is security, correctness or api_compat; or a rejection |
| `major` | Should be fixed before merge | Change-request wording |
| `minor` | Should be fixed eventually | Suggestion wording |
| `nit` | Optional | "nit:", "optional", "consider" |

Severity matters for ordering, the attention estimate and cost weights in calibration. Fidelity counts all substantive findings, whatever their severity.
